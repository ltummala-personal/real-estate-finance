Real Estate Project Finance

Technical documentation & functional specification

Django 5.2 · PostgreSQL 17 · Docker Compose · Single-company POC · Currency: INR · Time zone: Asia/Kolkata

1. Overview

The application keeps all of a real estate company's accounts in one place. Money moves in and out through bank, cash and card accounts, and is tied to projects (sites/developments) and categories (materials, labour, sales receipts, etc.). Data arrives in many shapes — bills, invoices, bank statements, CSV/Excel ledgers and manual entries — and the application converts that unstructured or semi-structured data into a single structured ledger stored in PostgreSQL, from which statistics can be pulled at any time.

Goals

  • One ledger: every rupee in or out is a Transaction, whatever its source.
  • Many inputs: PDF/image bills and invoices (text extraction + OCR), bank statements (CSV/XLSX/PDF), CSV/XLSX ledgers, manual form entry.
  • Human in the loop: extracted data is staged and must be reviewed/approved before it reaches the ledger.
  • Traceability: every imported transaction links back to its original uploaded file, which stays downloadable.
  • On-demand statistics: filterable reports by month, project, category, account and vendor, with CSV export.
  • Private by default: runs locally in Docker, all processing (including OCR) on-box; no third-party APIs.

2. Feature catalogue

Dashboard

Money in, total spent, net cash flow, total budget, budget remaining; account balances (opening + in − out); project spend/receipts; recent transactions; count of entries awaiting review.

Bill / receipt import

PDF or photo (PNG/JPG/TIFF/WEBP). Text-layer extraction, OCR fallback for scans. Detects total, date, bill number, vendor, GSTIN.

Invoice import

Same pipeline as bills, labelled as invoice. Direction defaults to money out, editable during review (for sales invoices).

Bank statement import

CSV, Excel (.xlsx) or text PDF. Auto-detects header row and columns; supports debit/credit columns, signed amounts, Dr/Cr markers, running balance inference. Must be linked to an account.

CSV / Excel ledger import

Bulk load historical or external ledgers. Optional Category/Project columns are matched to master data by name/code.

Manual entry

Web form for cash payments, adjustments, receipts. "Save and add another" for fast keying.

Review & approval

Edit every extracted field, approve / reject / defer per row, or bulk approve all complete non-duplicates. Batches of 50.

Duplicate protection

Same file (SHA-256) cannot be uploaded twice; rows matching existing transactions are flagged and excluded from bulk approval.

Transactions register

Filter by date range, project, account, category, direction, source, free text; totals; pagination.

Reports & statistics

Totals; by month; by project with budget remaining; by category; by account; top 10 vendors; CSV export of the filtered set.

Document archive

List of uploads with status and pending/approved counts; download original; view text read from the document.

Master data (admin)

Projects (code, budget), Accounts (bank/cash/card, opening balance), Categories, Users.

5.4 Constraints & integrity

  • project_budget_nonnegative: CHECK budget ≥ 0.
  • transaction_amount_positive: CHECK amount > 0.
  • Unique: Project.code, Account.name, Category.name, SourceDocument.sha256, ExtractedEntry.transaction.
  • PROTECT on Transaction → Project/Account/Category and SourceDocument → Project/Account: master data in use cannot be deleted.
  • CASCADE SourceDocument → ExtractedEntry: staging rows go with their document.
  • SET_NULL Transaction → SourceDocument: ledger rows survive if a document record is removed.
  • Approval of multiple entries runs in a DB transaction with SELECT … FOR UPDATE to prevent double-posting.

8. Extraction rules (detail)

8.1 Header column detection

Header text is lower-cased, bracketed text removed, non-letters collapsed (e.g. Chq./Ref.No. → chq/ref no). Rules are tested in order; first match wins per column, and the first column for each field is used. A row is the header when it maps a date column and at least one of amount / debit / credit, within the first 40 rows.

1balance (ignored)balanceClosing Balance
2type^(dr/cr|cr/dr|debit/credit|type|transaction type|txn type)$Dr/Cr, Type
3debitwithdrawal|debit|^dr$|money out|paid outWithdrawal Amt., Debit Amount
4creditdeposit|credit|^cr$|money in|paid inDeposit Amt., Credit
5datedateTxn Date, Value Date
6reference\bref|chq|cheque|\butr\b|invoice no|bill noChq./Ref.No., UTR
7categorycategor|expense head|ledgerCategory
8project^projectProject, Project Code
9descriptionnarration|description|particular|detail|remark|memoNarration, Particulars
10counterpartyvendor|payee|party|merchant|beneficiary|supplier|customerVendor, Payee
11amountamount|\bamt\bAmount, Transaction Amount

8.2 Direction (money in / out)

  1. Debit/credit columns: net = credit − debit; positive → credit, negative → debit (note added if both present).
  2. Single amount + type column: dr/debit/withdraw/out/expense/payment… → debit; cr/credit/deposit/in/income/receipt… → credit.
  3. Signed amount only: if any negative values exist in the file, negative → debit, positive → credit.
  4. Otherwise all rows default to debit with a "please verify" note.
  5. PDF text statements: compare running balance with the previous balance (prev − amount = balance → debit; prev + amount = balance → credit). "Opening balance / B/F / brought forward" lines seed the balance.

8.4 Bill / invoice heuristics

FieldRule
TotalSearch (bottom-up) for labels in priority order: grand total, total amount payable, amount payable, net payable, total payable, invoice total, total due, balance due, amount due, net amount, total amount, total (ignoring sub-total / total tax / total qty). Take the last amount on that line, or on the next line. Fallback: largest decimal amount in the document (flagged).
DateLabels: invoice date, bill date, date of issue, inv date, receipt date, dated, date — first date after the label (same or next line). Fallback: first date anywhere.
Reference(invoice|inv|bill|receipt) (no|number|num|#) followed by an identifier containing a digit.
VendorFirst of the top 8 lines with ≥ 3 letters that isn't a title line (invoice, receipt, original, duplicate, page n…). Flagged as a guess.
GSTINIndian GSTIN pattern; up to 3 recorded in notes.
Description"Invoice/Bill <ref> from <vendor>".

11. Security controls

AreaControl
AuthenticationAll finance views use login_required; Django password validators; logout is POST-only with CSRF.
SecretsStartup fails without a real DJANGO_SECRET_KEY; secrets live in an untracked .env; DEBUG off by default.
Network exposureWeb bound to 127.0.0.1; DB on internal Docker network with no published port; container runs as non-root.
CSRF / clickjacking / sniffingCSRF middleware on all forms; X_FRAME_OPTIONS=DENY; nosniff; HttpOnly session and CSRF cookies.
File uploadPer-kind extension allow-list, size limit, magic-byte validation, random UUID storage names (no user-controlled paths), SHA-256 de-duplication.
File parsingPage/row/column caps; Pillow decompression-bomb protection; openpyxl read-only with defusedxml; OCR timeout; parser exceptions converted to safe messages.
File servingMedia is not served publicly; downloads go through an authenticated view with Content-Disposition: attachment.
InjectionORM-only queries; template auto-escaping (raw OCR text rendered escaped); CSV export prefixes cells starting with = + - @ tab/CR to stop spreadsheet formula injection.
Data integrityDB check constraints, PROTECT foreign keys, atomic approvals with row locks, human approval before posting.
PrivacyAll extraction runs locally; only last 4 digits of account numbers are stored.

Cloud deployments (§17) run behind Caddy with automatic HTTPS and set DJANGO_SECURE=true, which enables secure cookies, HTTPS redirect and HSTS. Still to do for wider production use: per-user object permissions if multiple teams share the system, off-site backups, and moving extraction to a background worker.

17. Cloud deployment & CI/CD pipeline

The cloud setup uses only open-source components and needs no vendor-specific services: any Ubuntu 24.04 virtual machine (Hetzner, DigitalOcean, OVH, Linode, AWS Lightsail, Azure/GCP VM, Oracle Cloud, or an on-premise server) runs the same Docker Compose stack used locally, with Caddy added in front for automatic HTTPS. GitHub Actions tests every change, builds the image, pushes it to GitHub Container Registry (GHCR), deploys to staging, tests there, and, after manual approval, deploys the same image to production.

Open-source stack

Docker Engine, Docker Compose, Caddy 2 (Let's Encrypt), PostgreSQL 17, Tesseract, Django, Gunicorn.

Minimum server size

2 vCPU, 4 GB RAM, 40 GB SSD per environment. OCR is the main CPU consumer.

Environments

staging (auto-deploy from main) and production (manual approval gate).

Release unit

One immutable image per commit: ghcr.io/<owner>/<repo>:<sha12>. Staging and production run the identical image.

scp -i ~/.ssh/ref_deploy_production "deploy@<production-ip>:/opt/real-estate-finance/backups/*" .\backups\

Restore a database backup

dc stop web
gunzip -c backups/pre-deploy-YYYYMMDD-HHMMSS.sql.gz | dc exec -T db sh -c \
  'psql -U "$POSTGRES_USER" -d postgres -c "DROP DATABASE IF EXISTS $POSTGRES_DB WITH (FORCE)" -c "CREATE DATABASE $POSTGRES_DB" && psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"'

The restore drops the current database. Practise it on staging first and take a fresh backup before restoring in production.

18. Cloudflare deployment (Workers + Containers)

18.1 Why Cloudflare Containers, not Pages

The error Could not detect a directory containing static files (e.g. html, css and js) appears when Cloudflare (Pages, or Workers Builds without a wrangler.jsonc) tries to treat the repository as a static website. This application is a Python/Django server with OCR (Tesseract) and PostgreSQL, which cannot run as static files or as plain JavaScript Workers. It runs on Cloudflare Containers: a small Worker receives every request and forwards it to the existing Dockerfile image running in a container managed by a Durable Object.

Run Django + Gunicorn + TesseractCloudflare Containers (standard-1: ½ vCPU, 4 GiB)Runs the unchanged Docker image.

DatabaseManaged PostgreSQL reachable over the Internet with TLS, e.g. Neon (free tier) or SupabaseContainer disk is ephemeral; Cloudflare has no hosted PostgreSQL.
Uploaded bills/statementsCloudflare R2 bucket (S3-compatible, via django-storages)Files must survive container restarts.

  • A single named instance (primary) serves all traffic, so migrations never run concurrently. It sleeps after 15 minutes without requests; the next request cold-starts it (migrations + boot, typically 10-40 s).
  • The Worker builds the container environment at start-up: DJANGO_ALLOWED_HOSTS, DJANGO_CSRF_TRUSTED_ORIGINS, DJANGO_SECURE=true, DJANGO_USE_X_FORWARDED_HOST=true, plus the secrets listed below. It overwrites any client-supplied X-Forwarded-* headers.
  • On first start, python manage.py ensure_superuser creates the admin user from DJANGO_SUPERUSER_USERNAME/DJANGO_SUPERUSER_PASSWORD (it never changes an existing user).

18.3 Step-by-step setup

Prerequisites

  • Cloudflare account on the Workers Paid plan (required for Containers).
  • Node.js 20+ and Docker Desktop (running) on your laptop - only needed for deploying from the laptop.

1. Create the PostgreSQL database (Neon)

  1. Sign up at neon.tech → Create project (region close to your users, PostgreSQL 17).
  2. Copy the connection string, e.g. postgresql://user:password@ep-xxx.aws.neon.tech/neondb?sslmode=require. Use the direct (non-pooler) string so migrations work.

2. Log in and create the R2 bucket (PowerShell, project folder)

cd C:\Users\ltummala\Documents\Workspace\Personal\real-estate-finance
npm install
npx wrangler login
npx wrangler whoami                                  # shows your Account ID
npx wrangler r2 bucket create real-estate-finance-uploads

Create an R2 API token: dashboard → R2 → Manage API tokens → Create API token → permission Object Read & Write, restricted to the real-estate-finance-uploads bucket. Note the Access Key ID and Secret Access Key.

3. Edit wrangler.jsonc

  • name: must equal the Worker name in the dashboard if you connected the repo with Workers Builds.
  • R2_ACCOUNT_ID: your Account ID from wrangler whoami.
  • APP_HOSTNAMES: leave empty for *.workers.dev, or set e.g. finance.example.com when you add a custom domain.

4. Store the secrets (encrypted in Cloudflare; never commit them)

npx wrangler secret put DJANGO_SECRET_KEY            # paste: python -c "import secrets; print(secrets.token_urlsafe(64))"
npx wrangler secret put DATABASE_URL                 # paste the Neon connection string
npx wrangler secret put R2_ACCESS_KEY_ID
npx wrangler secret put R2_SECRET_ACCESS_KEY
npx wrangler secret put DJANGO_SUPERUSER_PASSWORD    # first admin password (user name: admin)
npx wrangler secret list

If the Worker does not exist yet, wrangler secret put offers to create it - answer yes.

5. Deploy

git add . ; git commit -m "Cloudflare Containers deployment" ; git push   # Workers Builds deploys automatically, or:
npx wrangler deploy                                  # from the laptop (Docker must be running)
npx wrangler containers list
npx wrangler tail                                    # live logs

Open https://real-estate-finance.<your-subdomain>.workers.dev. The first deploy can take several minutes while the image is provisioned; the first request then cold-starts the container. Sign in as admin, then create accounts, categories and projects in the admin.

6. Custom domain (optional)

# Domain must be on Cloudflare DNS. Dashboard: Workers & Pages → real-estate-finance → Settings → Domains & Routes → Add → Custom domain
# Then set APP_HOSTNAMES in wrangler.jsonc, e.g. "finance.example.com,real-estate-finance.<sub>.workers.dev", and redeploy.

Option B commands (PowerShell). Create a Cloudflare API token with the Edit Cloudflare Workers template plus Account → Containers → Edit and Account → Workers R2 Storage → Edit:

$repo = "<github-user>/real-estate-finance"
gh api -X PUT "repos/$repo/environments/cloudflare"
gh secret set CLOUDFLARE_API_TOKEN --env cloudflare --repo $repo        # paste the token
gh secret set CLOUDFLARE_ACCOUNT_ID --env cloudflare --repo $repo --body "<account-id>"
gh variable set APP_URL --env cloudflare --repo $repo --body "https://real-estate-finance.<sub>.workers.dev"
gh variable set DEPLOY_TARGET --repo $repo --body "cloudflare"          # enables the job; "vm" enables §17 instead
gh workflow run ci-cd.yml --ref main --repo $repo
gh run watch --repo $repo

Optional approval gate: GitHub → Settings → Environments → cloudflare → Required reviewers. Without DEPLOY_TARGET, the workflow only runs tests (safe when using Workers Builds).
